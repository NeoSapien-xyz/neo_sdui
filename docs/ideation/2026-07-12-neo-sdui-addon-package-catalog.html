Sibling doc: 2026-07-11-neo-sdui-addon-architecture-ideation.html ideated the add-on machinery (NeoSduiAddon + compose(), a contract package, a ThemeExtension bag). That machinery has since landed (compose/neo_compose.dart, compose/neo_sdui_addon.dart, and the neo_sdui_media package all exist). This doc assumes the spine and asks the next question: given the guide's actual wire, which packages should ride on it?

Grounding Context

The MCP setup guide is a real, shipped wire document (example/mcp/mcp_document.dart) rendered by today's 13 core block types (header, text, cta, callout, media, card, steps, faq, tabs, row, column, group, spacer). Reading the wire closely — not the design in the abstract — surfaces four things the core roster cannot express, and every package below targets one of them.

What the wire actually contains (the demand signal):

  • Terminal commands smuggled into prose. Setup steps carry literal strings the user must reproduce exactly: npm install -g @anthropic-ai/claude-code, the server URL https://api.neosapien.xyz/mcp (repeated ~6×), run /mcp, claude mcp list, and a claude_desktop_config.json reference in Troubleshooting. Today they render as plain step captions — no monospace, no copy button, no way to avoid a typo. The Figma canvas confirms the intent: Command nodes with Copy affordances appear ~18–30×.
  • A phone/laptop contradiction. Three separate callouts say "Requires laptop for setup" / "Setup happens on your computer" — yet the guide is read inside the Neo mobile app, on the phone. The user reads the steps on one device and must perform them on another, with no bridge.
  • External destinations the wire can't open. The final cta "Contact Support" points at https://neosapien.xyz/support; steps name chatgpt.com, claude.ai/download, and OAuth sign-in flows. Core treats a screen:… action as in-app navigation, but has no sanctioned handler for an https:// one.
  • Answers that want emphasis. FAQ answers, callout bullets, and the "from NeoSapien" trigger phrase all lean on inline emphasis and links; core text renders a plain body only.
  • A funnel and a checklist hiding in plain sight. The intro page is a card→screen:chatgpt|claude|other chooser feeding per-client steps; the Figma frames wrap this in "4 Tasks", a "Circular progress indicator", and "Updating" chips. The guide is a linear setup funnel, but renders as stateless, un-instrumented content.

The invariant every package must respect. Core stays flutter + meta only; the wire carries semantics, never look or heavy capability (CONCEPTS.md). So each package below earns its separation by pulling a dependency core refuses to carry — a native plugin, a parser, a highlighter, a persistence layer — and each degrades to a core floor when absent (the requires/fallback model in neo_sdui_view.dart).

Library reality (context7-checked, 2026-07-12). Bases were verified rather than assumed: flutter_markdown (the old flutter.dev package) is discontinued — the live successors are markdown_widget, flutter_markdown_plus, and gpt_markdown; note markdown_widget transitively pulls flutter_highlight + highlight + url_launcher + visibility_detector. qr_flutter (QrImageView, QrVersions.auto, L/M/Q/H error correction, embedded-image overlay) is healthy and current. url_launcher (launchUrl/canLaunchUrl, native impls per platform) is healthy. Clipboard is Clipboard.setData from flutter/services — zero extra dependency, so copy itself is core-eligible; only highlighting forces a package.

Topic Axes

command surface
Exact strings — commands, config, URLs, prompts — that must be copied, not retyped.
device handoff
Bridging "read on phone" to "do on laptop" for the setup steps.
navigation
Opening external URLs / OAuth off the wire without breaking the app-owns-nav rule.
rich content
Emphasis, links, inline code in answers and body text.
stateful & instrumented
Progress that persists and a funnel that reports — beyond a stateless render.

1. neo_sdui_code — copyable command / config block

command surface Confidence 92% Complexity: Low flutter/services · +flutter_highlight (opt)
Description
Add a code block type: { "type": "code", "content": "npm install -g @anthropic-ai/claude-code", "language": "bash" }, rendered monospace with a tap-to-copy button (Clipboard.setData + a themed "Copied" confirmation). Because copy needs only flutter/services, the block is core-eligible — the actual package is the optional neo_sdui_syntax upgrade that re-registers code with flutter_highlight coloring for the claude_desktop_config.json case. Ship the floor first; the highlighter is the add-on.
Axis
command surface
Basis
direct: mcp_document.dart — commands live as bare steps captions (npm install…, the server URL ~6×, /mcp, claude mcp list, claude_desktop_config.json); Figma Command+Copy nodes ~18–30×. external: Clipboard.setData (flutter/services, zero-dep) verified core; flutter_highlight+highlight confirmed the live highlighting stack (context7). reasoned: a mistyped install command or server URL is a hard setup failure — copy removes the single most common drop-off in a CLI guide.
Rationale
Highest-value, lowest-cost package in the set: it directly unblocks the guide's dominant content (exact strings) and its cheap half needs no dependency at all. Establishes the "core floor + add-on upgrade" rung for text-like content, mirroring what neo_sdui_media already does for images.
Downsides
Splitting "copy" (core) from "highlight" (add-on) is a judgment call — if highlighting is deemed table-stakes, the whole thing is an add-on and core gains nothing. Copy on a phone needs a visible confirmation (toast/haptic) so the tap feels acknowledged; that is theme surface, not wire.
Confidence
92%
Complexity
Low (floor) · Low–Medium (syntax add-on)

2. neo_sdui_qr — phone→laptop handoff block

device handoff Confidence 84% Complexity: Low qr_flutter
Description
A qr block: { "type": "qr", "data": "https://api.neosapien.xyz/mcp", "caption": "Scan on your laptop" }, rendered with QrImageView. It turns the repeated "requires a laptop" dead-end into an action — the user scans the phone screen with their computer to jump the server URL (or a desktop-setup deep-link) across devices without retyping. Fallback when the add-on is absent: render data as a copyable line (idea #1's floor), so nothing breaks.
Axis
device handoff
Basis
direct: three callouts in mcp_document.dart — "Requires laptop for setup" / "Setup happens on your computer" — against a guide rendered in the phone app. external: qr_flutter / QrImageView verified current (auto version, L/M/Q/H correction, embedded-logo overlay) — context7. reasoned: cross-device handoff is the guide's structural problem; QR is the standard, zero-typing bridge.
Rationale
Solves a pain no core block can touch — the read-device ≠ act-device gap — with a tiny, well-scoped native-free package (qr_flutter is pure Dart painting). Non-obvious: the reflex is "write clearer steps," but the real fix is to move the URL to the right device. Doubles as an "open the guide on desktop" affordance elsewhere in the app.
Downsides
A raw server URL in a QR isn't itself the full setup — value depends on the app minting a genuinely useful desktop deep-link, which is app/ server work beyond the package. Encoding untrusted wire data into a QR is a mild trust surface (scannable link) — keep the block to first-party URLs, or validate scheme/host in the builder.
Confidence
84%
Complexity
Low

3. neo_sdui_launcher — url_launcher action handler

navigation Confidence 86% Complexity: Low url_launcher
Description
Core resolves a screen:… action as in-app navigation but has no owner for an https:// one. This add-on contributes an action handler (not a block) that intercepts URL-scheme actions on cta/card and opens them via launchUrl — external browser for support/marketing links, in-app tab for OAuth. It slots into the same NeoSduiAddon compose the block add-ons use, keeping the app-owns-in-app-nav rule (R14) intact while delegating the external slice to an opt-in package that carries the native plugin.
Axis
navigation
Basis
direct: mcp_document.dart — cta "Contact Support" → https://neosapien.xyz/support, and steps naming chatgpt.com, claude.ai/download, OAuth sign-in. external: url_launcher (launchUrl/canLaunchUrl, per-platform native impls) verified healthy — context7. reasoned: every guide eventually links out; making it a composable action handler avoids the app hard-coding URL handling per screen.
Rationale
Fills a real hole — the wire references external destinations the renderer can't act on — with the smallest sanctioned mechanism, and it generalizes: any future wire URL (privacy policy, app store, docs) just works. Establishes the precedent that add-ons can contribute action verbs, not only block builders.
Downsides
Needs the compose spine to support action-handler contributions, not just builders — a small contract extension the sibling doc flagged as YAGNI until an add-on needed it (this is that add-on). External-link opening is a mild security surface; restrict to https and known hosts, or confirm before launch.
Confidence
86%
Complexity
Low

4. neo_sdui_markdown — rich text / answers

rich content Confidence 78% Complexity: Medium markdown_widget / flutter_markdown_plus
Description
A richtext (or last-wins upgrade of text) that renders inline Markdown — bold, links, inline code — so FAQ answers, callout bullets, and the "from NeoSapien" trigger read with emphasis instead of as flat strings. Because markdown_widget bundles a syntax highlighter and link handling, this package could also subsume idea #1's syntax upgrade — one rich-content dependency instead of two.
Axis
rich content
Basis
direct: faq answers and callout.bullets in mcp_document.dart carry emphasis, quoted prompts, and a support link that plain text flattens. external: context7 — flutter_markdown is discontinued; live options are markdown_widget (bundles markdown+flutter_highlight+highlight+url_launcher+visibility_detector), flutter_markdown_plus (drop-in fork), and gpt_markdown.
Rationale
Unlocks expressive answer/body content the guide already implies, and the dependency verification is exactly why this matters: picking the dead flutter_markdown would have been the obvious-but-wrong move. Consolidating highlighting here (vs a separate neo_sdui_syntax) can shrink the ecosystem's dependency count.
Downsides
markdown_widget transitively pulls url_launcher — a content add-on quietly acquiring navigation power, which muddies idea #3's clean boundary; flutter_markdown_plus (lighter) may be the better base if links route through the launcher add-on instead. Markdown is only worth it if authors will actually write it — plain text covers most of today's copy, so this is the most speculative of the top four.
Confidence
78%
Complexity
Medium

5. neo_sdui_analytics — funnel instrumentation (no render)

stateful & instrumented Confidence 74% Complexity: Medium host analytics SDK (injected)
Description
A package that contributes zero block builders and instead wraps the registry: it decorates each builder to emit impression/tap events through a host-injected sink. The guide is a measurable funnel — which AI a user picks (screen:chatgpt|claude|other), whether they reached Troubleshooting, whether the "Contact Support" CTA fired — and this makes that funnel observable without any block knowing it's being watched.
Axis
stateful & instrumented
Basis
direct: the intro page is a card→screen:* chooser feeding per-client steps, ending in Troubleshooting/FAQ/Support — a classic drop-off funnel authored entirely on the wire. reasoned: a registry-wrapping decorator is the one add-on shape that needs no new block type and no wire change — it composes over builders the way the sibling doc's compose() already folds them.
Rationale
The only way to know if the guide works (do users finish setup?) is to measure it, and a cross-cutting decorator add-on gets that for free across every block, current and future. Non-obvious because add-ons are assumed to be block-shaped; this one is behavior-shaped.
Downsides
Needs a stable event sink injected by the host (analytics SDK is app-owned, kept out of the package) — a small contract for passing the sink through compose(). Wrapping every builder risks over-firing; needs a sampling/opt-in per type. Privacy: memory-adjacent content must never enter event payloads.
Confidence
74%
Complexity
Medium

6. neo_sdui_progress — steps become a persisted checklist

stateful & instrumented Confidence 68% Complexity: Medium shared_preferences
Description
A last-wins upgrade of steps that makes each item tappable and remembers completion across app launches — the 12-step ChatGPT setup becomes a checklist the user can pause and resume, with a progress indicator. Absent the add-on, steps renders as today's static list.
Axis
stateful & instrumented
Basis
direct: the per-client setups are 6–12 sequential steps (an inherently linear, resumable task); the Figma frames wrap the guide in "4 Tasks", a "Circular progress indicator", and "Updating" chips. external: shared_preferences for per-guide completion state. reasoned: a multi-step setup that spans a phone→laptop context switch is exactly where users lose their place.
Rationale
Turns a static guide into a tool that respects the user's real interruption pattern (do a step, switch to laptop, come back). It's the first package that gives the wire memory, which the "Updating"/progress design language clearly anticipates.
Downsides
Most speculative of the survivors — it assumes users want to track guide progress, which is unproven; a guide short enough to finish in one sitting doesn't need persistence. State keyed to wire content is brittle if the server re-authors steps (need a stable step id on the wire). Introduces client-side state into a system whose whole premise is a stateless render — a real architectural cost, not just a dependency.
Confidence
68%
Complexity
Medium

7. neo_sdui_prompt — tap-to-copy suggested-prompt chips

command surface Confidence 72% Complexity: Low flutter/services (or fold into #1)
Description
A prompt block for the "try this" example prompts — "What do you know about me from Neosapien?", "Summarise everything I said today." — rendered as a chip/card that copies the prompt on tap so the user pastes it straight into their AI. Same copy mechanism as idea #1, but semantically distinct: a suggestion to run, not a command to execute.
Axis
command surface
Basis
direct: "Try your first prompt: …" recurs across every client screen in mcp_document.dart, and the intro page lists seven quoted example prompts as cards; Figma "Suggested Prompt" nodes appear ~36×. external: Clipboard.setData (zero-dep). reasoned: the prompts are the guide's payoff — the thing the user actually does with the connection — so reducing them to copy-paste-able chips is high-leverage, low-cost.
Rationale
Converts the guide's most-repeated call-to-action into a one-tap gesture, and the Figma signal (36 nodes) says the design already treats prompts as a first-class element, not prose.
Downsides
Largely idea #1's machinery in different clothing — arguably a variant of the copyable block rather than its own package; keep it separate only if prompt chips diverge visually enough to justify a distinct type. Zero-dep, so like #1 it may belong in core, not an add-on at all.
Confidence
72%
Complexity
Low
