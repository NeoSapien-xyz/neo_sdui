figwire's theme half — turning one Figma read into both the wire and a paste-in NeoSduiTheme

Date: 2026-07-15 Topic: figwire-theme-companion Mode: repo-grounded Focus: should figwire also emit a NeoSduiTheme; one skill or two

The question in one line: figwire reads a Figma selection and writes the semantic wire. Can the same skill also hand back the look — a NeoSduiTheme literal to paste into the app — accumulated across many screens fed part by part, ending in one complete theme?

Verdict

Viable — strongly. The theme is the exact complement of the wire. figwire already reads every pixel from Figma and then discards it to honor the Iron Rule (no hex/px/font on the wire). The theme is precisely that discarded projection, kept instead of thrown away — near-free per screen, and it dodges a second read against a seat-capped Figma plan.

One skill, not two. Not "cram pixel logic into the wire classifier," and not "a separate skill that re-reads Figma." The fit is one ingestion → two projections, sharing a role ledger so the wire's role names and the theme's role slots can never drift, plus a terminal compile step that turns the cross-screen ledger into the paste-in Dart literal. This sharpens figwire's invariant rather than breaking it: "no pixels on the wire" stays; add "every pixel goes to the theme." See idea 1.

Grounding Context

Codebase context

  • The Iron Rule & the complement. figwire's contract forbids any #hex/px/font/gradient on the wire; the one visual signal it reads is accent-green → tone:"accent". Everything else about look is read and dropped. The theme is what you get by keeping the dropped half.
  • Existing split. neofig owns look→widget code for a single component; figwire owns semantics→wire. Neither emits a cross-screen NeoSduiTheme — that is the gap.
  • Seat cap. The Figma seat is hard-capped (~6 reads/month); the screenshot path is the everyday path. Any design that reads Figma twice per screen is a non-starter.
  • The target class is fixed and known. NeoSduiTheme is ~40 fields: role colors, a 4-slot type scale + mono, radius/space scales, card/group/grid surface treatments, cardGradient/groupGradient/accentGradient, the accents and icons maps, and motion. It already has copyWith and a .fallback() factory — the codegen target is a constructor literal shaped exactly like .fallback().
  • The coupling. The wire names roles (tone:"brand", emphasis:"high", icon:"sparkle"); the theme defines the pixels for those exact names (accents["brand"], groupGradient, icons["sparkle"]). A wire role with no theme slot renders flat; a theme slot no wire names is dead. The two outputs are joined at the role vocabulary.

External context (webfetch + context7, as requested)

  • Token layer > pixel scraping. Every mature Figma→code pipeline (Tokens Studio, Style Dictionary, the Figma Variables REST API) treats the variable/style layer as the source of truth and calls frame-scraping unreliable. Figma MCP already exposes get_variable_defs, get_shader_fill, get_shader_effect.
  • "Many screens → one theme" is a solved shape. Accumulate an intermediate token doc, then codegen once. A Claude-Code plugin (gregorymm/design-tokens) does exactly Figma→DTCG→Style Dictionary. Multi-mode/multi-theme = variable "modes" / Tokens Studio "themes" — the direct analog of neo's per-guide theme.
  • Flutter (context7). NeoSduiTheme is already the ThemeExtension analog (immutable + copyWith); a paste-in literal needs no lerp/ of(context) plumbing. Per-screen look differences resolve by handing a subtree a different theme, never by changing the wire.

1. One ingestion, two projections Recommended spine

A single figwire run reads the Figma selection once, then forks into two writers over the same in-memory node data: the wire writer (semantics → per-screen .json, unchanged) and the theme writer (look → appended to a cross-screen theme ledger). The theme logic lives in its own reference (references/theme-extract.md) and its own accumulator file — modular, but never a separate Figma reader. figwire's rule is unchanged and, in fact, sharpened: no pixels on the wire; every pixel goes to the theme.

Axis
A1 · skill topology
Basis
reasoned: the wire and theme partition the same Figma data with zero overlap — semantics vs look — so one read serves both; a second skill can only re-derive what the first already held.
Rationale
Directly answers "one skill or two." The seat cap makes double-reading untenable, and the role coupling (idea 3) makes independent generation unsafe. Shared ingestion is the only topology that satisfies both.
Downsides
Identity risk — figwire is known as "the no-pixels skill," and bolting a pixel-emitting output onto it can confuse the contract. Mitigation: pixels never touch the wire file; they land in a separate theme artifact, so the wire's rule reads unchanged.
Confidence: 88%Complexity: Medium

2. Cross-screen token ledger, compile once

Because you feed screens "part by part," the theme cannot be written per screen — it is singular and cross-screen. Each run appends its role→value observations to a running JSON ledger (a sidecar, e.g. .theme/ledger.json): "screen 4 says accent = #00F1A0, radiusLg = 16, title = 22/w600." A separate terminal command (figwire theme compile) reconciles the whole ledger and emits the one NeoSduiTheme(...) literal. This is the standard Figma→tokens→codegen two-stage shape.

Axis
A3 · cross-screen accumulation
Basis
external: the accumulate-then-codegen-once pipeline (DTCG token doc → Style Dictionary → platform output) is the established Figma-to-code shape; gregorymm/design-tokens and Tokens Studio both stage it this way.
Rationale
Makes "feed me screens part by part, give me one theme at the end" a first-class flow instead of a manual merge. The ledger also becomes the diff surface for conflicts (idea 5).
Downsides
A persistent sidecar is state the user must not lose between runs; needs a clear reset/scope story (per-guide? per-app?). Ledger location and lifecycle need naming.
Confidence: 84%Complexity: Medium

3. Shared role registry couples wire ↔ theme

The single strongest reason the two outputs must share a pass: they are joined at the role vocabulary. When the wire writer emits tone:"brand", that same run registers a brand slot in the theme ledger and drops the observed hue into it. The ledger is the one registry both writers draw from, so a wire role can never ship without its theme pixels, and a theme accent can never sit unused. Generating wire and theme independently is exactly how they drift.

Axis
A4 · output & coupling
Basis
direct: accentFor resolves a tone against accents[tone] first, then built-in accent/critical; an unmapped tone returns null and "the text stays its default (non-accent) look." A role the wire names but the theme skips silently renders flat.
Rationale
This is the correctness spine that forces idea 1. It also gives the theme a gateable invariant (idea 7): every role named across all accumulated wires must resolve in the compiled theme.
Downsides
Couples the two writers' internal data model — a refactor of one now touches the shared ledger schema. Acceptable: the coupling is real in the runtime already, this just stops pretending otherwise.
Confidence: 86%Complexity: Medium

4. Variables/styles-first extraction, pixel fallback

Fill the ledger from the token layer when it exists: get_variable_defs for color/number/type variables and bound styles, get_shader_fill/get_shader_effect for the gradients that map onto cardGradient/groupGradient/accentGradient. Only when a file binds no variables do you degrade to reading exact values from get_design_context/REST, and only then to eyeballing the screenshot. Prefer structure over scraping, exactly as the design-token ecosystem does.

Axis
A2 · extraction source
Basis
external: "Using Figma's Variables API provides a programmatic, maintainable approach … compared to scraping"; variables are the published single source of truth. Figma MCP ships dedicated get_variable_defs and shader tools.
Rationale
Turns most of the ~40 fields into a near-deterministic lookup when a design system is wired, and cleanly captures the branded gradients neo's theme already has slots for — no hand-transcribing stops.
Downsides
Many real files bind no variables; then you're on the expensive/ manual path, and exact hex needs a design-context read (seat cost). Reading variables can itself be an extra MCP call to budget.
Confidence: 80%Complexity: Medium

5. Reconciliation branches into per-guide modes

When two screens disagree on a role, the compiler must tell apart two cases: drift (screen A's accent #00F1A0 vs B's #00F0A0 — near-dupes, pick a canonical value and move on) versus intent (the "troubleshooting" guide is genuinely amber where the base guide is green). Drift collapses to one value; intent branches into a second theme — or a copyWith override layered on the base. This is the per-guide-theme question made concrete, and it mirrors Figma variable "modes."

Axis
A3 · cross-screen accumulation
Basis
external: multi-mode/multi-theme (variable modes, Tokens Studio "themes") is a first-class ecosystem concept — a matrix of values per role, one column per mode; the direct analog of neo handing each guide its own NeoSduiTheme.
Rationale
Prevents the accumulator from silently averaging two guides into a muddy single theme. A near-dupe threshold auto-merges; anything past it surfaces as "same role, real difference — base value or a mode?"
Downsides
The drift-vs-intent threshold is a heuristic; too tight spams the user with conflicts, too loose merges away a real brand difference. Needs a human confirm on the borderline, not full automation.
Confidence: 72%Complexity: High

6. Emit a paste-in NeoSduiTheme literal + coverage report

The compile step writes a NeoSduiTheme(...) constructor literal shaped exactly like .fallback() — copy-paste straight into the app — plus a coverage report saying which of the ~40 fields were filled from tokens, which were inferred, and which are // TODO(theme): because Figma couldn't answer. Colors and gradients fill cleanly; the honest weak spot is the type scale: many observed font sizes must cluster into title/subtitle/body/caption + mono, which is inference that wants a human glance before sign-off.

NeoSduiTheme(
  accent: Color(0xFF00F1A0),        // from variable "brand/primary"
  surface: Color(0xFF202423),       // from variable "surface/1"
  danger: Color(0xFFFF5A5F),        // from variable "status/error"
  accents: {'brand': NeoAccent(Color(0xFF7A5CFF))},   // wire tone:"brand"
  cardGradient: LinearGradient(...),                  // from get_shader_fill
  title: TextStyle(fontSize: 22, fontWeight: FontWeight.w600),  // inferred cluster — confirm
  // TODO(theme): gridLine — no variable bound; read from screenshot or set by hand
)
Axis
A4 · output & coupling
Basis
reasoned: the class already carries copyWith + a .fallback() literal, so the codegen target is a known, fixed constructor shape — no intermediate format or build step needed to reach paste-in (context7 confirms no lerp/of() plumbing for a static theme literal).
Rationale
Delivers exactly what the user asked for — a theme to drop in the app — and the coverage report keeps the tool honest about what it guessed versus what it read.
Downsides
Type-scale clustering is genuinely lossy and the most likely field to be wrong; over-trusting it ships a subtly-off theme. Keep it flagged low-confidence, never silent.
Confidence: 83%Complexity: Medium

7. The theme's gate: round-trip render + role-drift lint

figwire gates the wire because a bad block vanishes silently. The theme's failure mode is different: it renders, but wrong (wrong hex, wrong radius). So it needs its own two gates. Round-trip render — render an accumulated wire under the compiled theme and put it beside the Figma screenshot for an eyeball diff (the theme's analog of the preview PNG). Role-drift lint — assert every tone/emphasis/icon named across all accumulated wires resolves in the compiled theme, and flag theme slots no wire uses. That lint is the theme-side of the existing vocabulary gate.

Axis
A5 · theme-side verify
Basis
direct: figwire's verify already renders a structural preview PNG and runs a strict vocabulary gate; the theme reuses that render harness with a real theme instead of the test default, and extends the gate's role check to the theme side.
Rationale
Closes the loop the wire gate can't: an on-vocabulary wire under a wrong-hex theme passes every existing check yet looks broken. Only a render-vs-source diff catches it.
Downsides
Pixel-diffing against a Figma screenshot is fuzzy (fonts, anti-aliasing) — it's an eyeball aid, not a hard assert. The role-drift lint, by contrast, is exact and cheap.
Confidence: 78%Complexity: Medium
