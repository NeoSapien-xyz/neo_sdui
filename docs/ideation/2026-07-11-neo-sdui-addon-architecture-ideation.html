Grounding Context

Today neo_sdui is one flat Flutter package, dependencies pinned to flutter + meta only. A large upcoming MCP setup guide (Figma canvas ≈ 12348×11989 px, far past the 12 current block types) is the demand signal: many new block/screen types and heavier native deps (video, cached images, charts, maps) are coming, and they cannot land in a core that must stay dependency-minimal.

Codebase Context. The engine already carries the seams an ecosystem needs, and they are the leverage points every idea below builds on:

  • Open registry — BlockRegistry maps wire type→builder; register() is documented "last wins (lets add-ons replace a core block)"; copy() extends without mutating (block_registry.dart:23-27).
  • Capability gating on the wire — blocks carry requires (feature→min version) + a fallback subtree; _requiresMet degrades instead of crashing (neo_sdui_view.dart:87-113). This is Adaptive Cards' model, already ours.
  • HostConfig injection — NeoSduiTheme holds all pixels off the wire, passed via NeoSduiScope (neo_sdui_theme.dart:3-6).
  • Designed-but-unbuilt — neo_sdui_video (registers a video builder, brings video_player); the image loader is currently core.

The gaps a multi-package future exposes (the pain the ideas target): the host hand-populates a Map<String,int> capabilities map disconnected from what add-ons register; register is a silent last-wins clobber with no collision protection; the host wires N add-ons by hand with no aggregation; NeoSduiTheme is a closed value object an add-on can't extend without editing core; federation and cross-package version compatibility are prescribed but unbuilt; there is no cross-package test harness (a video widget has no decoder in the test binding).

Industry grounding. Flutter federated plugins (app-facing / platform-interface / implementation split; extends+verify-token so the interface evolves non-breaking), Melos / pub workspaces, VS Code's static contributes manifest, Adaptive Cards requires/fallback/version, Firebase's BoM, Sentry's opt-in integrations, Stripe's core-loader + component split, and Linux kmod vermagic all solve the same shape: a thin core that holds only the contract + registry, with capability delegated to opt-in packages and version compatibility negotiated explicitly.

1. The NeoSduiAddon manifest + compose() spine

registration Confidence 88% Complexity: Medium converged ×3 frames
Description
Each add-on exports a single plain-Dart value object — NeoSduiAddon(types: {...}, capabilities: {...}, themeExtension: ...) — bundling everything it contributes. The host calls NeoSdui.compose([videoAddon, imageAddon, …]) once; the helper folds every add-on into a ready {registry, capabilities} for NeoSduiView, derives the capability map from the same declarations that register the builders, and returns a never-throws diagnostics report (type collisions, orphaned capabilities, load order). This is the spine ideas 2–7 plug into.
Axis
registration
Basis
direct: "Host wires N add-ons manually… No aggregation helper" and "No capability↔registration binding… an add-on can register a block yet the host forget to declare its capability" (neo_sdui_view.dart:32,51-52; grounding gaps). external: VS Code's static contributes manifest (host reads the declaration before running code) and Sentry's integrations: […] opt-in array.
Rationale
Collapses the two most-cited multi-package footguns — manual N-wiring and the capability↔registration drift — into one call, with a value object + fold that respects flutter+meta / no-codegen. As package count climbs toward the MCP guide's scale, per-add-on wiring is the thing that breaks silently first; making registration the single source of the capability map removes the whole class of "video renders fallback because the host forgot the cap" bugs.
Downsides
Adds a small public API surface (the NeoSduiAddon shape) that then carries its own compatibility promise. The diagnostics-report affordance is only useful if hosts actually read it in debug. Reporting the derived manifest onward to the MCP server (so it authors only-supported blocks) is a natural extension but pulls in app-owned transport — keep it out of the package.

2. Extract neo_sdui_contract — the only semver-gated surface

boundaries Confidence 80% Complexity: Medium-High converged ×3 frames
Description
Pull the stable contract surface add-ons actually touch — the BlockBuilder typedef, BlockNode, NeoSduiTheme shape, NeoSduiScope.of, NeoAction, the reserved-key constant — into a tiny neo_sdui_contract package. The renderer and every add-on depend on the contract, never on each other. Borrow Flutter's plugin_platform_interface trick: new contract methods ship with default implementations behind a private verify-token, so the interface can grow without a major bump across all add-ons.
Axis
boundaries
Basis
external: Flutter federated plugins — "the platform interface is the versioned contract; breaking it is a major bump across all impls" — plus extends+verify-token for non-breaking method addition (docs.flutter.dev; pub.dev/packages/plugin_platform_interface). direct: the grounding's federation risk — "a core bump would silently break out-of-sync add-ons."
Rationale
Turns "which core version does this add-on need?" into one small, rarely-changing number and sets the blast radius of every future core change. The bet: what actually must be stable is narrow, so isolating it lets the renderer evolve aggressively while 50 add-ons keep compiling.
Downsides
A three-package split is real coordination overhead and premature before the first native add-on exists — the grounding itself says federate "only when neo_sdui_video actually lands." Drawing the contract line too small forces later breaking moves; too large re-imports the churn problem. The verify-token pattern adds boilerplate implementers must follow.
Confidence
80%
Complexity
Medium-High

3. The image add-on is a last-wins media swap, not a new type

boundaries Confidence 90% Complexity: Low converged ×2 frames
Description
The reflex for "I want an image add-on" is a new block type + a new capability + wire negotiation. Invert it: media already exists in core rendering Image.network, and the registry's register is already "last wins (lets an add-on replace a core block)." So neo_sdui_image just copy()s the registry and re-registers the same media type with a cached / blurhash / zoom builder. No new wire type, no requires, no capability negotiation — and if the add-on is absent, rendering silently degrades to Image.network. Formalize this as the ecosystem's cheapest add-on shape: core ships a zero-dep floor for every semantic; a heavy add-on upgrades it by re-registering the same type. New types are reserved for genuinely new semantics (charts, maps).
Axis
boundaries
Basis
direct: block_registry.dart:23 — register is "last wins (lets add-ons replace a core block)"; media.dart:9-10 — core is images-only; prior ideation — cached_network_image "pulls native deps so it would be an add-on." Directly answers the live image-add-on decision (and the previous turn's "how do I get cached_network_image here").
Rationale
Establishes the cheapest rung in the ecosystem — "replace a core block's implementation" needs zero new machinery, and resilient-degrade is automatic (uninstall the enhancer, the floor renders). Every future perf / native-dep swap follows this template instead of minting a type and a capability.
Downsides
Last-wins is order-sensitive and silent today — two add-ons both re-registering media clobber without warning (idea 1's diagnostics report is the mitigation). A pure replacement can't add new wire fields the enhanced look needs unless those fields were already semantic on media.
Confidence
90%
Complexity
Low

4. NeoSduiTheme extension bag (Flutter's ThemeExtension)

contracts Confidence 85% Complexity: Low converged ×3 frames
Description
Give NeoSduiTheme one new field — a type-keyed Map<Object, ThemeExtension>, exactly as Flutter's own ThemeData.extensions works — plus a theme.extension<T>() lookup. An add-on ships its own look struct (VideoControlsTheme, ChartPalette) and reads it namespaced by type; core never grows a new slot. The extension can still derive its pixels from the role palette rather than hardcode them, so the client-owns-the-look invariant holds.
Axis
contracts
Basis
external: Flutter's ThemeExtension<T> / ThemeData.extensions — the framework's sanctioned answer to third-party theme slots (api.flutter.dev). direct: grounding — "NeoSduiTheme is a closed value object… cannot extend it without editing core," and the plan's own flag "NeoSduiTheme slot churn."
Rationale
Removes core as the bottleneck for every add-on's look, reusing a pattern already native to Flutter (no new dependency, no codegen). Each heavy add-on (video, charts, maps) owns its palette end to end; the core theme file stops being something everyone has to edit.
Downsides
Type-keyed lookups are stringly-adjacent — a missing extension must degrade to a sensible default, not throw. Two add-ons could define overlapping extension types; the convention (one extension type per add-on, namespaced) has to be documented.
Confidence
85%
Complexity
Low

5. Degrade-conformance harness — test the contract, not the decoder

distribution Confidence 82% Complexity: Medium converged ×3 frames
Description
Cross-package golden testing was refused because a video widget has no decoder in the widget-test binding. Invert what's under test: don't test the add-on's real pixels — test its degradation contract. A shared harness renders a document against a registry with and without the add-on and asserts: add-on absent → the declared fallback subtree renders (identically to core's degrade path); capability unmet → fallback; unknown type → recurse-fallback-else-skip; and the composed manifest is internally consistent (every declared type has a capability and vice-versa). The heavy widget gets a smoke test against a fake player.
Axis
distribution
Basis
direct: grounding — "video golden-testing refused because video_player has no decoder in the widget-test binding… goldens only guard new-vs-new"; the degrade path (_buildOne: unmet → recurse fallback) is pure Dart and testable (neo_sdui_view.dart:87-113). reasoned: an add-on's real value is its degrade behavior, and that logic is decoder-free — so the untestable heavy widget is the wrong target; the contract is the right one.
Rationale
Turns "add-ons can't be tested" into "add-ons must prove they degrade correctly" — the property that actually protects users when an add-on is missing or version-short. Ships as a shared test util every add-on reuses, so package N inherits package 1's CI story, using the same never-throws "collect every issue" shape already in validation.dart.
Downsides
It deliberately does not test the real rendered add-on — a video that decodes wrong but falls back right still passes, so the smoke test against a fake player is not optional. Building a stub-registry harness is more than a one-file change.
Confidence
82%
Complexity
Medium

6. Version handshake — package version is capability version

negotiation Confidence 75% Complexity: Medium converged ×2 frames
Description
Two version notions already drift: the wire says requires: {video: "1.2"} (major.minor) but the gate matches int-major only (int.tryParse(split('.').first)). Collapse them: neo_sdui_video advertises its own package/contract version as the capability version, compose() diagnoses when an add-on's contract version mismatches the running core (kmod vermagic style — a named diagnostic, never a blank box), and the render-time gate is widened from int to major.minor so requires: {video: "1.2"} means what it says.
Axis
negotiation
Basis
direct: neo_sdui_view.dart:104-113 — _requiresMet parses major only, while the wire requires is major.minor (Adaptive Cards). external: Linux kmod vermagic (refuses modules built against an incompatible kernel) and VS Code engines.vscode compat ranges.
Rationale
Removes a second version ledger nobody will maintain and closes the current major-only-vs-major.minor mismatch, making pub version the single negotiation currency. The vermagic diagnostic converts a mystifying production render failure into a loud compose-time message.
Downsides
Coupling capability version to package version is rigid — a purely internal refactor that bumps the package shouldn't necessarily bump the semantics the client speaks. Widening the gate to major.minor touches the resilience-critical _requiresMet path and needs its own degrade tests.
Confidence
75%
Complexity
Medium

7. Authoring-side fallback-completeness lint

negotiation Confidence 80% Complexity: Low
Description
Take the zero-knowledge flip literally: the server authoring the wire has no idea which add-ons a given client build carries. The only safe consequence is that every non-core block type on the wire must carry both requires and a fallback. Add that as a rule to the existing pure-Dart, never-throws validation.dart: any block whose type isn't in the core roster and lacks a fallback/requires is a reported issue. This converts "resilient degrade" from an aspiration into a checkable authoring contract — no runtime, no codegen.
Axis
negotiation
Basis
direct: extends the validator that "never throws — returns every issue at once" (validation.dart:1-2,18). external: Adaptive Cards' requires/fallback/version authoring model, where a missing fallback degrades badly on old hosts.
Rationale
The cheapest possible enforcement point — a rule in a validator that already exists — and it makes the OTA / MCP-guide world (blocks authored server-side for clients that may not have the add-on) safe by construction. The MCP guide authors many block types; this catches the missing fallback before it ships instead of after a user sees a blank space.
Downsides
The validator needs to know the "core roster" to distinguish core from add-on types — a coupling to the registry it doesn't have today. A strict rule may over-report during local development where the author knows the add-on is present; it should be an advisory issue, not a hard failure.
Confidence
80%
Complexity
Low
